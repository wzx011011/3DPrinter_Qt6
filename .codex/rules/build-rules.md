# Build Rules

This project has one canonical full verification path.

## Canonical Command

Run full verification with:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/auto_verify_with_vcvars.ps1
```

## Canonical Build Directory

Use only:

```text
build/
```

## Rules

- Do not create alternate build directories.
- Do not use alternate full-build scripts.
- Do not bypass `scripts/auto_verify_with_vcvars.ps1` when claiming full build verification.
- Do not clean or delete `build/` unless the user explicitly asks for that operation.
- Documentation-only phases may use lightweight checks instead of a full rebuild, but must say that no full rebuild was run.

## Canonical Verify Pass Criteria (Gate Truth: 13 Blocking Suites)

The pass condition of `auto_verify_with_vcvars.ps1` is: **all 13 suites report
0 failed AND the script exits 0** (each blocking suite fails the script with a
red message and a nonzero exit). Configure, build, the app-launch liveness
check, the conditional RenderBench stage, and the conditional slice regression
gate are blocking too. On success the script's final action is `exit 0`.

### Resolution record: import-time heap-corruption attribution (Q13, closed 2026-10-12)

The 2026-08-31 "deterministic import-time heap-corruption" in `AppToolTests` /
`ViewportContextMenuTests` was attributed with the debug toolset and closed at
its mechanism:

- **Tool path actually used** (PageHeap needs admin, which this environment
  does not have): cdb from the Windows SDK (the audit's "独立诊断器" option)
  for live crash stacks, the repaired `EarlyCrashDiag` (see below) for
  pre-main coverage, and `CrashHandlerWin` (fail-fast VEH + symbolized stack +
  minidump, `src/core/debug/CrashHandlerWin.cpp`) now installed in both
  suites' `initTestCase` so any future crash lands in
  `build/crash_dumps/crash_stack.log` + a `.dmp` instead of exiting silently.
- **Attribution evidence**: the crash was a fail-fast (`0xC0000409`,
  `int 29h` executed inside the test exe itself) raised while QTest invoked
  the FIRST test slot of `ViewportContextMenuTests`
  (`rhiAndSoftwareExposeTheSameContextSignal` — `RhiViewport`/`SoftwareViewport`
  construction + `metaObject()->indexOfSignal`), i.e. exactly the import-path
  family the verify comments described.
- **Root cause**: a stale mixed-object build, not application code. The
  crashing binary was an incremental mixture (objects from different
  compilation epochs); rebuilding the SAME source states consistently —
  HEAD and HEAD+fix alike — passes 3/3 runs every time. The mixture class is
  the AUTOMOC "weak moc tracking" documented on the single-file QtTest
  targets in CMakeLists.txt: moc outputs are regenerated by mtime-tracked
  autogen steps, and since the 2026-09-05 configure fast path a source-only
  change no longer forces a configure-time automoc rescan, so a binary could
  pair stale `mocs_compilation.obj` metadata (offsetof-based Q_PROPERTY
  offsets) against freshly compiled consumers — corrupting memory at the
  first QObject construction of the run.
- **Mechanism-level fix**: the canonical verify now deletes every
  `build/*_autogen/timestamp` probe after the configure fast path, forcing
  CMake's RERUN_AUTOGEN step on this run's first ninja invocation — moc
  outputs are regenerated and mismatching objects rebuild, so a canonical run
  can no longer emit a mixed-layout binary.
- **Escalation recipe when the timestamp probe is NOT enough** (re-confirmed
  2026-10-13, P4 session): a stale mixed state can survive the
  autogen-probe deletion (the crashing binary flapped clean/crashing across
  RElinks of the SAME source, ~30-50% per process, at drifting phases).
  `git stash`-based A/B does NOT rule the mixture out — stashing sources
  never removes the stale objects. The proven stronger recipe: delete
  `build/CMakeFiles/` wholesale, `touch CMakeLists.txt`, re-run configure
  (inside the vcvars env), rebuild — every object recompiles against the
  current headers. Verified on the 2026-10-13 state: AppToolTests 6/6
  clean after the recipe (previously crashing across relinks), then all 14
  suites + the three-layer slice gate green. Do NOT attribute such crashes
  to hardware/source before running this recipe once.
- **Verification**: `ViewportContextMenuTests` 3/3, `AppToolTests` 3/3 on
  consistent builds; `E2EWorkflowTests` 32 passed / 0 failed / 0 skipped
  (Q12 probe: prerequisites present on this host, so every slice test really
  ran). All three suites then converted to red-exit blocking in the verify
  script in the same change.

## Slice Regression Gate (part of the canonical verify)

`auto_verify_with_vcvars.ps1` ends with a conditional slice regression gate
(`scripts/perf/run_slice_gate.ps1`). It fires when uncommitted changes or the
commits since the last green gate run touch the slicing surface (SliceService,
PreviewViewModel, EditorViewModel, `src/cli/*`, ProjectService,
PresetService, the OrcaSlicer submodule pointer, PerfBench.cpp, and the
gate's own files).

- Correctness layer (hard fail, exit 1): headless `owzx-cli` slices of
  `bench_sphere_400k.stl` + `Block20XY.stl` with pinned config are normalized
  by `tools/gcode_compare.py` and compared field-exact against the committed
  golden baseline `tests/data/slice_gate_baseline.json`.
- Efficiency layer (hard fail, exit 2): PerfBench slice stage, min-of-N
  wall clock (default N=3, `OWZX_SLICE_GATE_REPEATS`), vs baseline thresholds
  (slice_ms +25%, preview_parse_ms +10%; one automatic re-measure round before
  failing — docs/perf-baseline.md noise rules).
- Step-profile layer (P4, hard fail, exit 2, added 2026-10-13): four
  representative models (sphere_400k / overhang_tower / grid_20x100k /
  block_20xy), one PerfBench profile round each, comparing per-step wall
  clock from `SliceService::sliceStepTimeline()` against
  `baseline.step_profiles` (`steps_ms` keyed by the §6d step keys). A step is
  a regression only when it exceeds +30% AND the baseline step is >= 20 ms
  (small steps are noise-exempt); one breaching round triggers an automatic
  profile re-measure, and only a breach in BOTH rounds exits 2 (same rule as
  the efficiency layer). A step KEY appearing or disappearing means the
  engine's `set_status` wording changed (upstream submodule bump) — that
  always fails and is re-golded only via `-UpdateBaseline` after human
  review. The tower tier enables `enable_support` inside PerfBench (support
  generation is its workload); per-step baseline numbers live in
  docs/perf-baseline.md.
- Exit codes: 0 pass / 1 correctness regression / 2 efficiency or step-profile
  regression / 3 infra error. Any nonzero exit fails the whole verify.
- `OWZX_SLICE_GATE=0` skips; `OWZX_SLICE_GATE=force` runs regardless of the diff.
- Re-golding after an INTENDED slice-output change (engine upgrade, config
  default change, engine step-text change): run
  `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/perf/run_slice_gate.ps1 -UpdateBaseline`
  on a green build and commit the rewritten `tests/data/slice_gate_baseline.json`
  together with the change. A missing baseline is auto-established (yellow)
  from the current build on the next gate run.
- Gate state (last green commit) lives in `build/perf_out/slice_gate_state.json`;
  per-run details land in `build/perf_out/slice_gate_report.json`.

## Expected Environment

- Windows 10/11.
- Visual Studio 2022 MSVC toolchain.
- CMake and Ninja.
- Qt 6.12.0 (LTS, win64_msvc2022_64) installed at `.deps\Qt6.12\6.12.0\msvc2022_64`
  (M2.5 G1 switch, 2026-10-13; anchors: `scripts/auto_verify_with_vcvars.ps1`
  candidate list, `CMakeLists.txt` third_party fallback branch,
  `.github/workflows/tag-build.yml`). Rollback = restore the previous base's
  anchors — the 6.10 candidates were retired in M2.5 G5 (2026-10-14); their
  history lives in `docs/qt612-upgrade-notes.md`, do not re-add them.
  Facts that must survive the next base bump:
  - aqtinstall from PyPI (3.3.0) cannot install Qt 6.11+: Qt changed the
    online-repo folder layout and aqt fixed it only in git master (PR #1000;
    verified locally with 3.3.1.dev166). Local installs: use
    `pip install git+https://github.com/miurahr/aqtinstall.git`; CI pins
    `aqtsource:` on install-qt-action until a fixed PyPI release ships.
  - Qt 6.12's supported minimum CMake for USING Qt is **3.25**; the repo
    builds with CMake 3.21 only through the deliberate
    `QT_FORCE_MIN_CMAKE_VERSION_FOR_USING_QT=3.21` override (configure emits
    Qt's official "not officially supported" WARNING — expected, non-fatal).
    CMake >= 3.25 upgrades must revisit this override.
  - C++17 remains the supported consumer standard for Qt 6.12 (no C++20 gate
    found in the installed configs/headers; the full 6.12 build compiles with
    `CMAKE_CXX_STANDARD 17`).
  - `windeployqt` deployments in `build/` are Qt-version-locked: after an
    anchor switch, stale DLLs from the previous base (seen as stale 6.10
    DLLs at the 6.10→6.12 switch) make every exe fail with
    0xc0000139 (entry-point not found) until the next canonical verify
    redeploys with the new `$qtRoot`.
- Prebuilt OrcaSlicer dependency prefix as configured by the project CMake files.
- Git on PATH at configure time: the from-source build applies
  `patches/orcaslicer/*.patch` onto the pristine `third_party/OrcaSlicer`
  submodule checkout (see `cmake/ApplyOrcaSlicerPatches.cmake`).

## RHI Rendering Backend Commitment

- The supported rendering configuration is **Windows + D3D11, a single
  backend**. The backend selector probes D3D11-first
  (`src/qml_gui/Renderer/RhiBackendSelector.cpp`); that is the product
  commitment, not an accident of the code.
- D3D12 is **not** part of the commitment: it crashes at QQuickWindow
  swapchain init (0xC0000005) on AMD Radeon APU (mainstream integrated)
  graphics — confirmed on a real machine in v5.7 Phase 211. It remains
  reachable only as an explicit debug opt-in via `OWZX_RHI_RENDERER=d3d12`
  (with `OWZX_D3D12_DEBUG` for the debug layer), not as a default candidate.
- Non-D3D11 backends (Vulkan/OpenGL/Metal) and non-Windows CI are
  deliberately out of scope until a product decision re-opens them (dev
  plan 2026-10-10 §5). Do not widen the backend matrix or "fix" gate
  failures by adding backend candidates without that decision.

## OrcaSlicer Submodule

- The submodule stays a pristine upstream checkout; the gitlink pins the
  upstream baseline commit and carries no OWzx edits.
- All OWzx compatibility changes live in `patches/orcaslicer/*.patch` and are
  applied to the submodule working tree automatically at configure time.
  Configure is idempotent (fingerprint stamp `.owzx-patches-applied` plus a
  dirty-tree check); an out-of-sync submodule fails configure loudly instead
  of building an unknown tree.
- After changing the patch series, regenerate the baseline state with:
  reset the submodule to the pinned commit, drop untracked files created by
  the old series, and re-run configure.

## Verification Reporting

When reporting verification, state:

- Whether configure/build/app smoke/E2E tests passed.
- Whether `ViewModelSmokeTests.exe` was built only or also executed.
- Any environment-dependent checks that were skipped or require manual validation.
